Failover mode: AGENT (lease-based). The Go agent holds the Lease
"{{ include "pg.fullname" . }}-leader" as the sole authority for which pod is
primary, and drives PostgreSQL directly (pg_ctl / pg_basebackup / pg_rewind). Inspect:

  kubectl -n {{ .Release.Namespace }} get lease {{ include "pg.fullname" . }}-leader \
    -o jsonpath='{.spec.holderIdentity}'   # the current primary pod
  kubectl -n {{ .Release.Namespace }} get endpoints {{ include "pg.fullname" . }}  # points at the primary

NOTE: this release uses podManagementPolicy: Parallel, which is immutable on an
existing StatefulSet. If you are upgrading from a chart 1.x release that ran
failoverMode: repmgrd, read the 2.0.0 upgrade note in CHANGELOG.md first -- the
StatefulSet has to be recreated with --cascade=orphan.

{{- if eq (include "pg.usesDeprecatedRepmgrValues" .) "true" }}

DEPRECATED VALUES: your values file still uses the "repmgr:" block. Chart 2.0.0 renamed it
to "ha:" -- the name no longer matches what runs, since the failover agent is native and
repmgr is gone from the image (#290, #291). Almost every "repmgr.*" key still works for now:
each one is merged over its "ha.*" counterpart, so most 1.x files need no values change.

The exception (#298 security review): five security keys REFUSE the old spelling outright,
because a stale alias would silently override -- and downgrade -- a security control. If your
file sets any of these under "repmgr.agent.", the render fails until they move to "ha.agent.":
podCidr, control.allowedClientCNs, control.restore.allowedClientCNs,
control.restore.admissionPolicy.enabled, control.restore.admissionPolicy.acknowledgeUnbounded.
podCidr in particular is a required customization on CNIs outside 10.0.0.0/8, so a 1.x file
carrying it needs that one edit before this upgrade.

One rule to know while both names work: where a key is set under BOTH spellings, the
"repmgr:" one wins -- even over a --set, which Helm normally ranks highest. The chart cannot
tell your value from its own default by then, and preferring "repmgr:" is what keeps a 1.x
file working. So MOVE each key (delete the old one in the same edit) rather than adding the
new spelling next to it, or rename the whole block at once:

  helm get values -o yaml -n {{ .Release.Namespace }} {{ .Release.Name }} > values.yaml
  # then change the top-level "repmgr:" key to "ha:" -- nothing nested changes
  # (-o yaml matters: the default output prefixes "USER-SUPPLIED VALUES:", and the schema
  #  leaves additionalProperties open, so that stray key would be accepted in silence)

See "Renamed values: repmgr.* -> ha.*" under Upgrade and migration in the pg chart README
(pgvector shares pg's templates and defers to it for the migration detail).
Keys that were REMOVED rather than renamed still fail the render under either name.
{{- end }}
